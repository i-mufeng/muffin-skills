# Frontend UI Design

交付可运行、符合产品语境、在真实内容与多种视口下仍然稳定的界面。视觉润色服务于理解和操作，不以堆叠卡片、渐变、阴影或装饰来代替信息架构。

## 开始前

先读取现有代码、设计系统、品牌资产和相邻页面。明确用户、核心任务、信息优先级、目标设备和必须支持的状态；用户给出的设计稿和现有产品规范优先于本 Skill 的风格建议，但不能覆盖基本可用性与无障碍要求。

需要做视觉方案或调整视觉细节时，读取 [references/visual-principles.md](references/visual-principles.md)。参考图中的 35 条技巧已在其中整理并校正：它们是按场景选用的手段，不是必须全部出现的装饰清单。

实现或验收前端时，读取 [references/quality-gates.md](references/quality-gates.md)，按其完成响应式、状态、键盘、对比度、内容韧性和视觉回归检查。

## 工作方式

1. 先确定体验骨架：页面主任务、内容顺序、导航、主要动作、次要动作和危险动作。数据密集型工具优先扫描与操作效率，内容或品牌页面才强调叙事与沉浸感。
2. 用现有组件和 token 形成一致的网格、间距、字体、颜色、圆角、阴影与动效。没有系统时建立一组小而明确的语义 token，避免逐元素随意取值。
3. 先完成语义结构和完整状态，再做视觉表现。至少覆盖加载、空、错误、无权限、禁用、成功、长文本、极端数据和资源失败；只实现与当前产品流程相关的状态。
4. 控制视觉强调。每个区域通常只有一个最强动作或视觉焦点；通过位置、字号、字重、留白和对比建立层级，颜色与装饰只作辅助。
5. 使用真实或具有代表性的内容与素材。不要用大量同质占位卡片制造“完成感”，也不要让图片、图表或插画承担本应由文字和结构表达的信息。
6. 在目标技术栈内实现完整交互，保留现有工程约定。图标优先使用项目已有图标库，复杂领域逻辑优先使用成熟库。
7. 通过浏览器验证，而不只检查源码。至少检查窄手机、宽手机、常见桌面和宽桌面；操作键盘焦点、滚动、菜单、弹窗、表单和异步状态，并修复溢出、遮挡、跳动和不可达控件。

## 设计判断

- 先解决信息架构与交互问题，再解决视觉问题。删减、分组、改写标签往往比加效果更有效。
- 60/30/10 配色、双倍间距、双倍圆角等可作为起点，不是数学定律；以品牌、内容密度、平台习惯和实测效果为准。
- 阴影应取背景色相并保持低透明度；但边框、色面、留白或层级关系能表达分组时，不必加阴影。
- 卡片只用于真正独立、可重复、可选择或可操作的单元。页面章节、表单每一行和所有文字块不应自动卡片化。
- 渐变、毛玻璃、叠图、背景纹理和头像描边仅在能改善层级或可读性时使用；必须同时检查对比度、性能与降级效果。
- 图表只在比较、趋势、组成或分布比纯文本更清楚时使用，并提供数值、标签或等价文本；不要把单个数字包装成无意义的环形图。
- 图标用于加速识别，不替代含义不明的文字。陌生图标提供标签或 tooltip；同组图标保持尺寸、描边、视重和容器一致。
- 动效用于状态变化、空间关系和反馈，时长克制，并尊重 `prefers-reduced-motion`。

## 完成标准

只有在以下条件都满足时才算完成：主流程可操作；信息层级清楚；所有相关状态存在；键盘与触摸均可用；文本、图像、控件在目标视口不重叠或溢出；颜色不是唯一的信息载体；对比度与目标尺寸达到参考中的最低线；最终页面已经过真实浏览器截图检查。
