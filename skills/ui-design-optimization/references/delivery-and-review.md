# 设计交付与验收

## 设计质量检查

在写代码前确定主任务、内容优先级、目标设备、现有品牌和一条视觉主张。例：“面向项目负责人的高密度工作台，以清晰表格、克制青绿动作和暖灰背景建立稳定感。”这只是说明方式，不是默认所有产品青绿配色。

检查首屏：两秒内能认出产品、当前所在位置、关键内容与下一步操作。工作台不套营销 Hero；品牌页面按任务采用真实素材、字号节奏和叙事。减少无意义装饰不等于把所有内容变成灰色。

排版优先中文可读性、稳定字号阶梯与一致行高；数字列按比较任务对齐，必要时等宽数字。间距用项目已有尺度，组内小于组间；不要全局强制双倍间距或特定字体。卡片用于有边界的对象，页面章节可直接通过留白和分隔组织。

用一页代表性内容检验方向后再扩展。截图评审按“阻断 → 主要层级/流程 → 一致性 → 微调”处理，避免不停换色却不解决任务路径。

## 状态和交互

对本次涉及的组件覆盖适用状态：default、hover、pressed、focus-visible、selected、disabled、loading、empty、error、success。区分首次无数据与筛选零结果，错误提供能执行的恢复路径。

主流程与可恢复失败流程都实际操作。弹窗有初始焦点、焦点约束、关闭与焦点返回；筛选会改变结果；保存反馈与实际本地状态一致。异步变化不跳布局，减少动态效果下仍可操作。必要的状态文本、表单标签和错误提示不能因“少文字”被删掉。

## 复核矩阵

| 层级 | 至少验证什么 | 能证明什么 |
|---|---|---|
| 工程 | 项目既有类型检查、构建、必要行为测试 | 源码可编译与所测逻辑 |
| 色彩 | 实际正文/按钮/状态/焦点色对及语义 | 指定组合对比度与角色合理性 |
| 组件 | 两组内容/状态，关键组合跨情境，API/事件 | 可复用的输入输出与状态行为 |
| 浏览器 | 主流程、失败恢复、键盘、资源与控制台 | 当前浏览器下可操作 |
| 视觉 | 桌面/手机真实截图，长中文、数字、空/满数据 | 所检查页面的布局与视觉质量 |
| 线上/业务 | 仅在授权且实际运行时记录 | 对应环境和真实服务的验收 |

视口起点：1440×900 与 390×844，补查 320 宽重排及 768 宽中间状态；已有项目的支持矩阵优先。数据表可在自己的容器滚动，不能以隐藏全局 overflow 掩盖截断。200% 放大需实际检查，缩小截图不是放大测试。明暗主题仅在支持时均验收；截图不能代替键盘行为与屏幕阅读器验证。

WCAG 2.2 AA 2.5.8 是 24×24 CSS px 或满足规定例外；重要触控操作建议 44×44 及以上，但不能把 WCAG 2.5.5 的 44×44 AAA 写成 AA 要求。详见 [AA 最低目标](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) 与 [AAA 增强目标](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html)。

只运行与当前改动相关且项目要求的检查；测试应断言用户结果，不只匹配 CSS 类名或模板文本。自动无障碍扫描可辅助，但不等于完整合规。

## 交付文档应很短但可用

放在项目现有设计文档目录：目标及视觉取舍、token 来源、组件清单（props/emits/slots/状态）、页面组合关系、启动方式、验证命令/结果/截图、未验证边界。无需为每个按钮生成独立长文。

最终说明哪些已运行、哪些仅静态检查、哪些没做。预览没有完成时明确写原因；不以 skill 校验通过冒充设计品质证明。

## 可直接使用的请求

> 使用 $ui-design-optimization，在当前 Vue 项目中完成项目工作台设计稿。沿用现有设计系统，页面与组件展示共用源码；给出配色角色、可复用组件与关键状态，完成类型检查、构建和桌面/手机浏览器验收。使用本地样例数据，设计说明放文档。

## 独立评估场景

技能大改后可在临时目录用以下真实请求验证行为，而不是只检查文档格式：

1. 空白项目：“做中文项目管理工作台，要精致且不过分彩色，组件以后还能复用。”检查是否产生真实 Vue、组件 API、清晰主任务及浏览器证据。
2. 已有 Element Plus + `--brand-*` token 项目：“改善列表与筛选。”检查是否保留现有栈、不引入第二套库、不换全站主题。
3. “只能用三种颜色，仍要展示八个分类及成功失败状态。”检查是否解释品牌色与数据色区别并保留真实信息，而非随意删类别。
4. “只给设计意见，暂时不要改代码。”检查是否尊重边界。
